IA agentique pour devs
Programme Module 1
0/12

Passez de l'usage des agents IA à leur conception.

Une formation pratique pour développeurs, de l'agent de code jusqu'à l'agent en production : tool calling, MCP, sub-agents, evals, garde-fous. Chaque module ajoute une brique au même projet.

  • 11 modules et un projet final
  • 12 à 14 semaines à 4–8 h par semaine
  • TypeScript pour tous les exemples
Commencer le module 1 Voir le parcours

À qui elle s'adresse

Développeurs qui codent déjà au quotidien et utilisent Copilot, Cursor ou Claude Code, sans avoir encore construit de système agentique eux-mêmes. Tous les exemples et projets sont en TypeScript.

Prérequis

Git, une clé API chez un fournisseur de LLM (budget indicatif : 10 à 30 € pour toute la formation), Node 20+ et TypeScript.

Ce que vous saurez faire

  • Déléguer du vrai travail à un agent de code, et savoir quand ne pas le faire
  • Appeler un LLM par API en maîtrisant contexte, coût et latence
  • Donner des outils à un modèle et obtenir des sorties structurées fiables
  • Écrire une boucle agentique from scratch, puis avec un framework
  • Exposer vos systèmes via un serveur MCP
  • Orchestrer des sub-agents quand c'est justifié
  • Mesurer la qualité avec des evals et sécuriser un agent en production

Comment suivre chaque module

Lire les notions clés, faire les exercices (courts, 30 à 60 min), puis livrer le projet. Un module est validé quand tous ses critères de réussite sont cochés.

Votre progression est enregistrée dans ce navigateur. Pas le temps une semaine ? Décalez tout : mieux vaut un module fini en deux semaines que deux modules survolés.

Le parcours

Ouvrez un module pour voir ses notions, ses exercices et son projet. Cochez les critères au fur et à mesure.

UtiliserMaîtriser les agents qui existent

  1. Passer de l'autocomplétion à la délégation de tâches entières, en comprenant ce que fait l'agent sous le capot.

    Durée : 1 semaine

    Notions clés
    • Chat, autocomplétion, agent : trois usages différents. L'agent lit des fichiers, lance des commandes et itère seul. Il a besoin d'un objectif vérifiable, pas d'une consigne vague.
    • Le fichier de contexte projet (CLAUDE.md, règles Cursor, AGENTS.md) : conventions, commandes de build et de test, pièges connus. C'est le levier le plus rentable.
    • Plan puis exécution. Demander un plan, le corriger, puis lancer. On évite ainsi 20 minutes de code dans la mauvaise direction.
    • La boucle de vérification. Un agent qui peut lancer les tests se corrige seul. Sans tests, il devine.
    • Sub-agents, skills, hooks. Des agents spécialisés à contexte isolé, des procédures réutilisables, du code déterministe déclenché avant ou après une action.
    • Gestion du contexte. Une session longue se dégrade. Savoir compacter, repartir de zéro, découper.
    Exercices
    1. Écrire le fichier de contexte d'un de vos projets : stack, commandes, conventions, 3 choses à ne jamais faire.
    2. Faire la même tâche deux fois, avec et sans ce fichier. Noter les différences.
    3. Créer une skill pour une tâche répétitive (écrire un test, rédiger un message de commit).
    4. Définir un sub-agent « relecteur » avec des consignes strictes et lui faire relire une PR.
    5. Ajouter un hook qui lance le linter après chaque modification de fichier.
    Projet : Initialiser Repo Assistant

    Créez le dépôt du fil rouge en TypeScript en le faisant construire majoritairement par l'agent : structure, CI, tests, fichier de contexte.

FondationsParler aux modèles par l'API

  1. Savoir exactement ce qui se passe lors d'un appel à un modèle, et ce qu'il coûte.

    Durée : 1 semaine

    Notions clés
    • Un LLM est sans état. Chaque appel renvoie tout l'historique. La « mémoire » d'un chat, c'est vous qui la gérez.
    • Les rôles : system (règles du jeu), user, assistant. Le system prompt est votre contrat avec le modèle.
    • Tokens et fenêtre de contexte. Tout se compte en tokens : l'entrée, la sortie, les images, les outils. Plus de contexte = plus cher, plus lent, et parfois moins précis.
    • Coût. Les tokens de sortie coûtent plusieurs fois plus que ceux d'entrée. Le prompt caching réduit fortement le coût d'un préfixe réutilisé.
    • Latence. Temps jusqu'au premier token vs temps total. Le streaming améliore l'expérience perçue, pas le temps réel.
    • Paramètres : température, max tokens, stop sequences. Et le choix du modèle : un petit modèle rapide suffit souvent.
    • Erreurs : rate limits, timeouts, surcharges. Retry avec backoff exponentiel dès le premier jour.
    Exercices
    1. Appeler l'API en HTTP brut (curl), puis avec le SDK officiel. Lire la réponse JSON en entier.
    2. Construire un chat multi-tours en gérant l'historique à la main.
    3. Afficher le nombre de tokens et le coût estimé de chaque appel.
    4. Comparer trois modèles d'une même famille sur 5 questions : qualité, latence, coût.
    5. Activer le streaming et mesurer le temps jusqu'au premier token.
    Projet : La CLI ask

    Ajoutez à Repo Assistant une commande ask "question" qui interroge un LLM.

    Cours détaillé à venir.

  2. Traiter le prompt comme du code, et le contexte comme une ressource rare.

    Durée : 1 semaine

    Notions clés
    • Clarté avant astuces. Dire le but, le public, le format attendu et les contraintes. Expliquer le pourquoi d'une règle aide le modèle à l'appliquer aux cas imprévus.
    • Exemples (few-shot). Deux ou trois exemples variés valent mieux qu'un paragraphe de consignes. Attention : le modèle copie aussi leurs défauts.
    • Structurer l'entrée. Délimiter documents, instructions et données (balises XML, sections Markdown) pour éviter les confusions.
    • Laisser réfléchir. Demander un raisonnement avant la réponse, ou activer le mode de réflexion étendue, sur les tâches complexes.
    • Context engineering. Choisir quoi mettre dans la fenêtre : le bon fichier plutôt que tout le repo, un résumé plutôt que l'historique complet. Le contexte non pertinent dégrade la réponse.
    • Prompts versionnés. Un prompt vit dans un fichier, a un historique git et se teste. On ne le modifie pas « au feeling ».
    • Prompt injection. Un document fourni au modèle peut contenir des instructions. Les données ne sont jamais des ordres.
    Exercices
    1. Prendre un prompt vague, le réécrire en 3 versions de plus en plus précises. Comparer sur 5 entrées.
    2. Ajouter des exemples à un prompt d'extraction et mesurer le gain.
    3. Donner au modèle un fichier de 50 lignes puis de 5 000 lignes pour la même question. Observer.
    4. Cacher une instruction malveillante dans un fichier de code et voir si le modèle la suit. Puis durcir le prompt.
    Projet : Q&A sur un fichier

    Ajoutez ask --file chemin.ts "question" : l'assistant répond à des questions sur un fichier précis.

    Cours détaillé à venir.

  3. Donner des mains au modèle. C'est la brique sur laquelle repose tout agent.

    Durée : 1 semaine

    Notions clés
    • Le mécanisme. Vous décrivez des outils (nom, description, schéma JSON des paramètres). Le modèle ne les exécute pas : il renvoie une demande d'appel. Votre code exécute, puis renvoie le résultat au modèle.
    • La description est un prompt. Le modèle choisit un outil d'après son nom et sa description. Une description floue = des appels ratés.
    • Concevoir de bons outils. Peu d'outils, bien nommés, qui renvoient des résultats compacts et lisibles. Des messages d'erreur explicites que le modèle peut corriger.
    • Structured output. Forcer une réponse conforme à un schéma JSON (Zod). Indispensable dès qu'une réponse alimente du code.
    • Choix de l'outil : automatique, forcé, ou interdit. Appels parallèles quand les outils sont indépendants.
    • Validation. Toujours valider les arguments avant d'exécuter. Le modèle peut halluciner un chemin ou un paramètre.
    Exercices
    1. Implémenter un outil get_weather factice et faire le cycle complet à la main : demande, exécution, résultat, réponse finale.
    2. Donner deux outils aux descriptions ambiguës et observer les erreurs de choix. Réécrire les descriptions.
    3. Extraire des données structurées d'un texte libre (issue GitHub → titre, sévérité, composant) avec validation par schéma.
    4. Renvoyer volontairement une erreur depuis un outil et vérifier que le modèle se corrige.
    Projet : L'assistant explore le repo

    L'assistant n'a plus besoin qu'on lui donne le fichier : il le trouve seul.

    Cours détaillé à venir.

  4. Donner au modèle accès à plus de connaissances qu'il n'en tient dans sa fenêtre, sans tomber dans le RAG par réflexe.

    Durée : 1 semaine

    Notions clés
    • Le RAG (Retrieval-Augmented Generation) : chercher les passages pertinents, puis les injecter dans le prompt. Le modèle répond à partir de sources, pas de sa mémoire.
    • Embeddings et recherche vectorielle. Transformer du texte en vecteurs pour chercher par sens plutôt que par mot exact. Stockage : pgvector, SQLite-vec, Chroma, ou un simple fichier au début.
    • Chunking. Pour du code, découper par fonction ou classe plutôt que par nombre de caractères. Garder le chemin et les numéros de ligne en métadonnées.
    • Recherche hybride. Combiner mots-clés (BM25, grep) et vecteurs. Pour du code, le grep bat souvent l'embedding sur les noms exacts.
    • Agentic search vs RAG classique. Un agent qui cherche avec grep et lit des fichiers remplace souvent un pipeline RAG. Le RAG reste utile pour les gros corpus de documentation.
    • Mémoire. Court terme = l'historique de la conversation, à résumer quand il grossit. Long terme = des notes persistantes que l'agent lit et écrit (fichiers, base).
    Exercices
    1. Indexer la documentation d'une librairie que vous utilisez et poser 10 questions. Noter les échecs de récupération.
    2. Comparer trois stratégies de chunking sur le même corpus.
    3. Comparer, sur 10 questions sur votre code, l'outil search_code du Module 4 et une recherche vectorielle.
    4. Ajouter un résumé automatique de l'historique quand il dépasse un seuil de tokens.
    Projet : Recherche sémantique sur la codebase

    Cours détaillé à venir.

AgentsConstruire et orchestrer

  1. Écrire un agent sans framework, pour comprendre ce que tous les frameworks font à votre place.

    Durée : 2 semaines

    Notions clés
    • Un agent, c'est une boucle. Le modèle décide, votre code exécute l'outil, le résultat revient au modèle, jusqu'à ce qu'il réponde sans demander d'outil.
    • Workflow ou agent ? Si vous connaissez les étapes à l'avance, codez un workflow (enchaînement, routage, parallélisation). Réservez l'agent aux tâches dont le chemin est imprévisible. Le workflow est moins cher et plus fiable.
    • Critère d'arrêt. Nombre maximal d'étapes, budget de tokens, outil terminer explicite. Sans limite, un agent peut tourner en rond.
    • Planification. Demander un plan au départ, le tenir à jour dans le contexte (une liste de tâches), le réviser quand un résultat surprend.
    • Auto-vérification. Donner à l'agent un moyen de vérifier son travail : lancer les tests, relire le diff. C'est ce qui sépare un agent utile d'un agent qui produit du plausible.
    • Actions dangereuses. Distinguer lecture et écriture. Les écritures passent par une confirmation humaine ou un environnement jetable.
    const messages: Message[] = [{ role: "user", content: tache }];
for (let etape = 0; etape < MAX_ETAPES; etape++) {
  const reponse = await llm(messages, { tools: OUTILS });
  messages.push(reponse.message);
  if (reponse.toolCalls.length === 0) return reponse.text;
  for (const appel of reponse.toolCalls) {
    const resultat = await executer(appel); // validé, sandboxé, journalisé
    messages.push(resultatOutil(appel.id, resultat));
  }
}
throw new Error("Trop d'étapes");
    Exercices
    1. Implémenter la boucle ci-dessus avec les outils du Module 4. Afficher chaque étape dans le terminal.
    2. Donner une tâche impossible et vérifier que l'agent s'arrête proprement.
    3. Ajouter un outil update_plan et observer comment l'agent l'utilise sur une tâche en 5 étapes.
    4. Réécrire une des tâches de l'agent en workflow codé en dur. Comparer coût, durée et fiabilité sur 5 essais.
    Projet : Agent de triage et de correction d'issues

    À partir d'une issue, l'agent explore le code, localise le problème, propose un correctif et le vérifie.

  2. Écrire vos outils une fois et les rendre utilisables par n'importe quel client compatible : Claude Code, Cursor, un agent maison.

    Durée : 1 semaine

    Notions clés
    • Le problème résolu. Sans MCP, chaque outil est recodé pour chaque application. Avec MCP, un serveur expose des outils et n'importe quel client compatible les découvre.
    • Architecture. Un hôte (l'application), un client MCP par connexion, des serveurs. Trois primitives côté serveur : tools (actions), resources (données lisibles), prompts (modèles réutilisables).
    • Transports. stdio pour un serveur local lancé par le client. HTTP pour un serveur distant partagé, avec authentification (OAuth).
    • SDK officiels en Python et TypeScript. Un serveur minimal tient en une trentaine de lignes.
    • Tester. L'inspecteur MCP permet d'appeler vos outils sans client LLM.
    • Sécurité. Un serveur MCP tiers peut voir vos données et agir en votre nom. Lire son code ou n'installer que des sources de confiance.
    Exercices
    1. Installer un serveur MCP existant (filesystem, GitHub ou une base de données) dans votre agent de code et l'utiliser.
    2. Écrire un serveur MCP « hello world » avec un outil, le tester dans l'inspecteur.
    3. Ajouter une resource et un prompt au même serveur.
    4. Brancher votre serveur à Claude Code ou Cursor et le faire utiliser dans une vraie tâche.
    Projet : Le serveur MCP de Repo Assistant

    Exposez les capacités construites jusqu'ici via MCP.

    Cours détaillé à venir.

  3. Choisir un framework selon sa stack, et savoir quand ne pas en prendre.

    Durée : 1 semaine

    Notions clés
    • D'abord se demander si on en a besoin. Si le flux se dessine sans boucle ni branche, une fonction bien typée avec sortie structurée suffit. Un framework se justifie avec de l'état entre les tours, des reprises après crash, une validation humaine en cours de route ou plusieurs agents.
    • Ce qu'un framework apporte : persistance de l'état (checkpoints), reprise après redémarrage, streaming, human-in-the-loop, traces, intégration MCP.
    • Ce qu'il coûte : une abstraction de plus à déboguer, des mises à jour cassantes, parfois un verrouillage chez un fournisseur.
    • Choisir par la stack, pas par la mode. Le bon framework est celui qui vit là où sont déjà votre langage, votre cloud et votre fournisseur de modèles.

  4. Découper une tâche entre plusieurs agents quand c'est justifié, et seulement dans ce cas.

    Durée : 1 semaine

    Notions clés
    • Pourquoi des sub-agents. Deux raisons valables : isoler le contexte (le sub-agent explore 50 fichiers et ne renvoie qu'un résumé au parent) et paralléliser des sous-tâches indépendantes.
    • Le motif orchestrateur-travailleurs. Un agent principal découpe, délègue avec des consignes précises, puis agrège. Chaque sub-agent a son propre prompt, ses outils limités, son budget.
    • Le prix. Chaque agent multiplie les appels et les tokens. Un système multi-agents coûte souvent plusieurs fois plus qu'un agent seul pour la même tâche.
    • Les pièges. Consignes de délégation trop vagues, travail en double, sub-agents qui se contredisent, résultats trop longs qui saturent le parent. La qualité de la délégation fait tout.
    • Évaluateur-optimiseur. Un agent produit, un autre critique selon des critères explicites, on boucle jusqu'à validation. Utile quand le critère de qualité est clair.
    • Handoffs. Un agent passe la main à un autre, spécialisé, sans revenir au parent (support client, routage).
    Exercices
    1. Dans votre agent de code, lancer une tâche qui délègue à des sub-agents et lire comment les consignes sont rédigées.
    2. Faire explorer un gros dossier par un sub-agent qui renvoie un résumé de 200 mots max. Comparer la taille du contexte du parent avec et sans.
    3. Construire une paire rédacteur-critique sur la rédaction de messages de commit.
    Projet : Revue de PR multi-agents

    Un orchestrateur reçoit un diff et lance en parallèle des relecteurs spécialisés.

ProductionMesurer et sécuriser

  1. Remplacer « ça a l'air mieux » par un chiffre. C'est la compétence qui distingue un prototype d'un produit.

    Durée : 1 semaine, mais les evals commencent dès le Module 3

    Notions clés
    • Une eval = des cas + une façon de noter. Un jeu d'entrées représentatives, la sortie attendue ou des critères, et un score automatisé.
    • Trois façons de noter. Vérification par code (le JSON est valide, les tests passent, la bonne fonction est citée), comparaison à une référence, ou LLM-juge avec une grille précise.
    • Le LLM-juge est pratique mais biaisé. Le valider contre 20 à 30 jugements humains avant de lui faire confiance.
    • Évaluer un agent, pas seulement une réponse. Tâche réussie ou non, nombre d'étapes, outils appelés, coût, durée. Lire les traces des échecs : c'est là qu'on apprend.
    • Non-déterminisme. Un même cas peut réussir puis échouer. Lancer chaque cas plusieurs fois et regarder le taux de réussite.
    • Evals de régression. Chaque bug trouvé devient un cas de test. Le jeu grossit avec le projet.
    Exercices
    1. Reprendre les 10 questions du Module 3 et les noter automatiquement.
    2. Écrire une grille de LLM-juge pour la qualité des explications. Comparer ses notes aux vôtres sur 20 réponses.
    3. Lancer 5 fois le même cas d'agent et mesurer la variance.
    4. Changer un mot du system prompt et mesurer l'effet sur toute la suite.
    Projet : Suite d'evals en CI

    Cours détaillé à venir.

  2. Faire tourner un agent pour d'autres personnes sans risque, sans surprise sur la facture, et avec de quoi comprendre ce qui s'est passé.

    Durée : 1 semaine

    Notions clés
    • Modèle de menace. Tout contenu lu par l'agent (issue, fichier, page web, résultat d'outil) peut contenir une injection. Le danger naît quand l'agent combine données non fiables, accès à des données privées et capacité à agir ou à envoyer vers l'extérieur.
    • Moindre privilège. Chaque outil a le minimum de droits. Lecture seule par défaut. Jetons d'accès à portée limitée, jamais vos identifiants personnels.
    • Sandbox. Le code généré s'exécute dans un conteneur jetable, sans réseau sauf liste blanche.
    • Garde-fous déterministes. Des vérifications en code, avant et après chaque appel d'outil : chemins autorisés, commandes interdites, taille des sorties. On ne confie pas la sécurité au prompt.
    • Human-in-the-loop. Validation humaine pour toute action irréversible : merge, déploiement, suppression, envoi.
    • Observabilité. Tracer chaque exécution : prompts, appels d'outils, tokens, latence, erreurs. Sans traces, un agent en prod est une boîte noire.
    • Coûts. Budget par exécution et par jour, alertes, prompt caching, petits modèles pour les tâches simples, arrêt automatique en cas de boucle.
    • Fiabilité. Timeouts, retries, repli sur un autre modèle, idempotence des actions pour qu'une reprise ne fasse pas deux fois la même chose.
    Exercices
    1. Mener une attaque par injection sur votre agent via une issue piégée. Documenter ce qu'elle obtient.
    2. Mettre run_tests dans un conteneur sans réseau.
    3. Brancher un outil de traces (open source ou SaaS) et rejouer une exécution ratée à partir de sa trace.
    4. Simuler un agent qui boucle et vérifier que le budget l'arrête.
    Projet : Durcir Repo Assistant

Repo Assistant, brique par brique

Chaque projet ajoute une brique au même dépôt : un assistant qui comprend une codebase, répond à des questions dessus, trie les issues et propose des corrections. À la fin, vous avez un projet complet à montrer, pas quatorze scripts jetables.

  2. M2Commande ask : streaming, coûts, retries
  3. M3Q&A sur un fichier, prompts versionnés
  4. M4Outils list_files, read_file, search_code, commande triage
  5. M5Index sémantique, semantic_search, NOTES.md
  6. M6Agent de triage et de correction d'issues
  7. M7Serveur MCP : outils, resource repo://architecture, prompt review-pr
  8. M8Agent de triage porté dans un framework
  9. M9Revue de PR par un orchestrateur et trois relecteurs
  10. M10Suite d'evals bloquante en CI
  11. M11Sandbox, liste blanche, validation humaine, traces, budget
  12. FinalUn agent de bout en bout sur un vrai problème

Une brique s'allume quand tous les critères de son module sont cochés.

Projet final

Semaines 13–14. Concevoir seul, de bout en bout, un agent qui résout un vrai problème, le vôtre ou celui de votre équipe.

Choisir le sujet

Partez d'une tâche répétitive que vous ou votre équipe faites chaque semaine. Quelques pistes :

  • Un agent d'astreinte qui lit une alerte, fouille logs et code, et propose un diagnostic
  • Un agent de migration qui met à jour une dépendance dans plusieurs dépôts et ouvre les PR
  • Un agent d'onboarding qui répond aux questions des nouveaux arrivants sur la codebase et la doc interne
  • Un agent qui transforme les tickets produit en spécifications techniques et en tâches estimées
  • Une extension de Repo Assistant : déclenchement automatique sur chaque nouvelle issue via un webhook

Livrables

  1. Une note de conception d'une page. Le problème, pourquoi un agent plutôt qu'un workflow, l'architecture, les outils, les risques.
  2. Le code. Avec au moins un serveur MCP, une suite d'evals et les garde-fous du Module 11.
  3. Un tableau de résultats. Taux de réussite, coût moyen par tâche, durée, sur au moins 20 cas.
  4. Une démo de 5 minutes. Enregistrée ou en direct.
  5. Un retour d'expérience. Ce qui a marché, ce qui a échoué, ce que vous feriez autrement.

Grille d'évaluation

Utilité25 %Le problème est réel, l'agent fait gagner du temps mesurable
Conception20 %Choix agent vs workflow justifié, outils bien découpés
Qualité mesurée20 %Evals pertinentes, résultats honnêtes, échecs analysés
Sécurité15 %Moindre privilège, sandbox, validation humaine
Coût et fiabilité10 %Budget maîtrisé, gestion des erreurs, traces
Communication10 %Note, démo et retour clairs

Pour une session de groupe : présentation croisée des projets, chaque participant relit la note de conception d'un autre avant la démo.

Pourquoi ce module

La plupart des développeurs utilisent leur agent comme une autocomplétion améliorée. Le gain réel vient ailleurs : un agent bien configuré, à qui l'on donne un objectif vérifiable, livre une fonctionnalité testée pendant que vous faites autre chose. Ce module est aussi le plus rentable de la formation : ce que vous y apprenez sert dès le lendemain.

C'est enfin votre premier contact avec l'architecture agentique. Tout ce que vous verrez ici (boucle, outils, contexte, sub-agents, hooks) sera reconstruit de vos mains dans les modules 4 à 9.

Ce que vous saurez faire

  • Expliquer ce que fait un agent de code à chaque étape d'une tâche
  • Écrire un fichier de contexte qui améliore nettement les résultats sur votre projet
  • Formuler une tâche de façon à ce qu'elle soit vérifiable, et obtenir un plan avant le code
  • Créer une skill, un sub-agent et un hook, et savoir lequel choisir
  • Garder des sessions efficaces sur des tâches longues
  • Relire le travail d'un agent et reconnaître les tâches à ne pas déléguer

Prérequis

Node 20+, TypeScript, git, et un agent de code installé. Les exemples utilisent Claude Code ; les équivalents Cursor et Copilot sont indiqués quand ils existent. Les concepts sont les mêmes d'un outil à l'autre, seuls les noms de fichiers changent.

Leçon 1

Comment fonctionne un agent de code

Un agent de code est un LLM dans une boucle, équipé d'outils : il lit, cherche, modifie et exécute, puis regarde le résultat et décide de la suite.

Trois usages, trois niveaux de délégation

Usage Qui décide des étapes Exemple Quand l'utiliser
Autocomplétion Vous, ligne par ligne Copilot qui termine une fonction Code que vous savez déjà écrire
Chat Vous, question par question « Pourquoi ce type ne compile pas ? » Comprendre, explorer une idée
Agent L'agent, à partir d'un objectif « Ajoute la pagination à /users, tests compris » Tâche multi-fichiers avec un résultat vérifiable

La boucle, sur un exemple réel

Vous demandez : « Le test formatDate échoue, corrige-le. » L'animation en haut de la page du programme rejoue exactement cette séquence :

  1. Il lance les tests (outil Bash : npm test). Il lit la sortie : l'erreur porte sur les fuseaux horaires.
  2. Il cherche le code (outil Grep : formatDate). Deux fichiers correspondent.
  3. Il lit les fichiers (outil Read) : la fonction et son test.
  4. Il modifie (outil Edit) : il remplace getHours() par getUTCHours().
  5. Il relance les tests. Ils passent.
  6. Il s'arrête et vous résume ce qu'il a fait.

À chaque étape, le modèle ne fait qu'une chose : choisir l'outil suivant d'après tout ce qu'il a vu jusqu'ici. Ce n'est pas lui qui exécute les commandes, c'est l'application autour de lui. Vous coderez exactement cette boucle au Module 6.

Les outils de base

Presque tous les agents de code ont les mêmes : lire un fichier, lister ou chercher des fichiers, chercher du texte, modifier un fichier, exécuter une commande shell. S'y ajoutent parfois la recherche web, une liste de tâches interne et le lancement de sub-agents.

Les permissions

L'agent demande votre accord avant les actions à risque : modifier un fichier, lancer une commande. Vous pouvez autoriser certaines commandes une fois pour toutes (par exemple npm test) et en interdire d'autres. Règle de départ : autorisez la lecture et les tests, gardez la validation manuelle pour le reste tant que vous ne connaissez pas l'outil.

À retenir

Un agent est aussi bon que ce qu'il peut observer. S'il peut lancer les tests, il se corrige seul. S'il ne peut rien vérifier, il produit du code plausible et s'arrête.

Leçon 2

Le fichier de contexte projet

Le fichier de contexte est lu au début de chaque session : c'est le levier le plus rentable pour améliorer un agent sur votre projet, et il se rédige en 20 minutes.

Où il vit

Outil Fichier Portée
Claude Code CLAUDE.md à la racine (et dans les sous-dossiers si besoin) Projet, versionné dans git
Claude Code ~/.claude/CLAUDE.md Vos préférences personnelles, tous projets
Cursor .cursor/rules/*.mdc Projet
Plusieurs outils AGENTS.md Convention partagée par de nombreux agents

Ce qu'on y met

Ce qu'un nouveau développeur senior devrait savoir le premier jour, et que l'agent ne peut pas deviner en lisant le code : les commandes, les conventions non évidentes, les pièges, l'architecture en quelques lignes.

Ce qu'on n'y met pas

Ce que l'agent voit déjà (la liste des dépendances, le contenu des fichiers), des règles génériques (« écris du code propre »), et des pavés. Chaque ligne coûte du contexte à chaque session. Visez 50 à 150 lignes.

Exemple complet pour un projet TypeScript

# Repo Assistant

CLI TypeScript qui aide à comprendre une codebase et à trier des issues.

## Commandes
- `npm run dev -- <args>` : lance la CLI en local (tsx)
- `npm test` : tests Vitest, à lancer après chaque modification
- `npm run lint` : ESLint + vérification des types (tsc --noEmit)
- `npm run build` : compile vers dist/

## Architecture
- src/cli/ : commandes (une par fichier), parsing avec commander
- src/core/ : logique métier, sans dépendance à la CLI
- src/llm/ : seul endroit qui appelle un fournisseur de LLM
- tests/ : miroir de src/, un fichier de test par module

## Conventions
- ESM uniquement, imports avec extension .js
- Pas de classes sauf nécessité : fonctions pures + types
- Erreurs : on renvoie des objets Result, on ne lance pas d'exception dans src/core
- Validation des entrées externes avec Zod

## À ne jamais faire
- Committer une clé API ou un fichier .env
- Appeler un LLM ailleurs que dans src/llm/
- Modifier un test pour le faire passer sans le signaler

## Pièges connus
- Les tests qui touchent au réseau doivent mocker src/llm/client.ts

Le faire vivre

Quand l'agent refait la même erreur deux fois, ajoutez une ligne. Quand une règle n'a plus d'effet, supprimez-la. Relisez le fichier une fois par mois : il vieillit comme de la doc.

À retenir

Mettez-y ce que l'agent ne peut pas deviner, et rien d'autre.

Leçon 3

Formuler une tâche déléguable

Une bonne tâche pour un agent a un objectif précis, un périmètre, et un moyen de vérifier qu'elle est finie. Si vous ne savez pas dire à quoi ressemble « fini », l'agent non plus.

Les quatre ingrédients

  1. L'objectif : ce qui doit être vrai à la fin, pas les étapes pour y arriver.
  2. Le contexte : les fichiers concernés, la raison de la demande, les contraintes.
  3. La vérification : quels tests doivent passer, quelle commande lancer, quel comportement observer.
  4. Le périmètre : ce qu'il ne faut pas toucher.

Mauvais prompt, bon prompt

À éviter
Améliore la gestion des erreurs dans l'API.

Pas d'objectif mesurable, pas de périmètre. L'agent va modifier vingt fichiers au hasard.

À viser
Dans src/api/users.ts, les erreurs de validation renvoient un 500
au lieu d'un 400. Objectif : toute erreur Zod doit produire un 400
avec le format { error: string, fields: string[] }.

- Ajoute un test par cas (champ manquant, type invalide)
- npm test doit passer
- Ne modifie pas les autres routes

Objectif, contexte, vérification et périmètre : les quatre ingrédients sont là.

Plan d'abord, code ensuite

Sur toute tâche qui touche plus de deux fichiers, demandez un plan avant le code. Dans Claude Code, le mode plan (Maj+Tab pour basculer) fait lire et réfléchir l'agent sans rien modifier. Ailleurs, écrivez simplement : « Propose un plan, n'écris pas encore de code. »

Lisez le plan comme une revue de conception. Corriger une mauvaise approche à ce stade prend 30 secondes. La corriger après 400 lignes de code prend une heure.

Découper

Une tâche trop grosse donne un résultat moyen partout. Si le plan fait plus de 6 à 8 étapes, découpez en sous-tâches livrables séparément, chacune avec ses tests. Un commit par sous-tâche vous donne des points de retour faciles.

Donner des exemples

« Fais comme dans src/api/projects.ts » vaut mieux qu'un paragraphe de conventions. L'agent imite très bien le code existant, pour le meilleur et pour le pire : pointez-le vers vos meilleurs fichiers.

À retenir

Si vous ne savez pas dire à quoi ressemble « fini », l'agent non plus.

Leçon 4

Skills, sub-agents et hooks

Trois façons d'étendre un agent : une skill lui apprend une procédure, un sub-agent lui donne un assistant spécialisé, un hook exécute du code à coup sûr à un moment précis.

Besoin Outil Qui décide Exemple
Une procédure que vous répétez Skill L'agent (ou vous, via /nom) Écrire des tests selon vos conventions
Une tâche lourde à isoler du contexte principal Sub-agent L'agent principal délègue Relire une PR, explorer un gros dossier
Une règle qui doit s'appliquer à chaque fois Hook Votre code, jamais le modèle Lancer le linter après chaque modification

Skill : une procédure réutilisable

Un dossier avec un fichier SKILL.md. Seule sa description est chargée en permanence ; le reste n'entre dans le contexte que lorsque la skill sert. Vous l'appelez avec /write-test, ou l'agent la déclenche seul quand la description correspond à la demande. Les anciennes commandes (.claude/commands/*.md) fonctionnent encore, mais les skills les remplacent.

.claude/skills/write-test/SKILL.md :

---
name: write-test
description: Écrit des tests Vitest pour un module TypeScript. À utiliser quand on demande d'ajouter, compléter ou corriger des tests.
---

1. Lis le module et liste ses cas : nominal, limites, erreurs.
2. Crée ou complète tests/<même chemin>.test.ts.
3. Un describe par fonction exportée, un it par cas, noms en français.
4. Mocke src/llm/client.ts, jamais le reste.
5. Lance npm test et corrige jusqu'au vert.
6. Termine par la liste des cas couverts et de ceux laissés de côté.

Sub-agent : un assistant spécialisé à contexte isolé

Un sub-agent a son propre prompt, ses propres outils et sa propre fenêtre de contexte. Il travaille à part et ne renvoie qu'un résumé : l'agent principal garde un contexte propre. Idéal pour les tâches qui lisent beaucoup et concluent peu.

.claude/agents/reviewer.md :

---
name: reviewer
description: Relit un diff et signale bugs, failles et tests manquants. À utiliser après toute modification non triviale.
tools: Read, Grep, Glob, Bash
---

Tu es relecteur senior sur un projet TypeScript.
Lance `git diff main` puis lis les fichiers concernés.
Signale uniquement : bugs, failles de sécurité, cas non testés,
écarts avec CLAUDE.md. Ignore le style, le linter s'en charge.
Format : une liste « fichier:ligne — problème — gravité ».
Ne modifie aucun fichier.

Notez les tools : pas d'Edit ni de Write. Un relecteur qui ne peut pas modifier le code reste un relecteur.

Hook : du code déterministe

Un hook est une commande shell déclenchée par un événement : avant un appel d'outil (PreToolUse), après (PostToolUse), à l'envoi d'un prompt, à la fin d'une session. Il reçoit les détails de l'événement en JSON sur son entrée standard. Un hook PreToolUse peut même bloquer l'action.

La différence est fondamentale : une consigne dans CLAUDE.md, l'agent peut l'oublier. Un hook s'exécute toujours.

.claude/settings.json — linter après chaque modification :

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx eslint --fix \"$(jq -r '.tool_input.file_path')\""
          }
        ]
      }
    ]
  }
}

Équivalents ailleurs. Cursor propose des règles (.cursor/rules) et des modes personnalisés ; Copilot, des fichiers d'instructions. Les formats évoluent vite : vérifiez la documentation de votre outil avant de copier ces exemples.

À retenir

Une consigne peut être oubliée ; un hook s'exécute toujours.

Leçon 5

Gérer le contexte et les sessions

La fenêtre de contexte est la mémoire de travail de l'agent : tout ce qu'il a lu, lancé et dit s'y accumule, et plus elle se remplit, moins il est précis.

Les signes d'une session qui se dégrade

  • L'agent oublie une consigne donnée au début
  • Il refait une erreur déjà corrigée
  • Il mélange deux tâches de la session
  • Il devient plus lent et plus vague

Les bons réflexes

  • Une tâche, une session. Finie la fonctionnalité, on repart de zéro (/clear dans Claude Code, nouveau chat dans Cursor). Le fichier de contexte est relu, l'historique inutile disparaît.
  • Compacter plutôt que subir. /compact remplace l'historique par un résumé. Vous pouvez guider le résumé : /compact garde les décisions d'architecture et la liste des fichiers modifiés.
  • Écrire l'état sur disque. Pour une tâche de plusieurs sessions, faites tenir à l'agent un fichier PROGRESS.md : fait, en cours, reste à faire, décisions. La session suivante commence par « Lis PROGRESS.md ».
  • Pointer, ne pas coller. Donnez des chemins (src/api/users.ts) plutôt que de coller 300 lignes. L'agent lira ce qu'il faut, quand il le faut.
  • Déléguer l'exploration. « Utilise un sub-agent pour trouver où sont gérées les sessions, et résume-moi en 10 lignes. » L'exploration se fait hors de votre contexte principal.

Revenir en arrière

Committez avant chaque tâche déléguée. Si le résultat ne convient pas, git reset --hard et vous reformulez : c'est souvent plus rapide que de faire corriger une mauvaise piste. Claude Code propose aussi de rembobiner la conversation et les fichiers à un point antérieur (Échap deux fois).

Travailler en parallèle

Avec git worktree, vous pouvez faire tourner deux agents sur deux branches du même dépôt sans qu'ils se marchent dessus. Commencez par un seul agent : le parallélisme ne sert que quand vous savez déjà bien déléguer.

À retenir

Une tâche, une session. L'état important vit sur disque, pas dans la conversation.

Leçon 6

Relire, sécuriser, savoir ne pas déléguer

Vous restez responsable de chaque ligne qui part en production : l'agent écrit vite, c'est à vous de relire bien.

Relire un diff d'agent

L'agent produit du code qui a l'air juste. Les erreurs typiques sont donc subtiles :

  • Un test modifié pour passer au lieu du code corrigé
  • Un cas limite oublié : tableau vide, null, fuseau horaire, concurrence
  • Une dépendance ajoutée sans nécessité
  • Du code mort ou dupliqué : l'agent réécrit une fonction qui existait ailleurs
  • Une modification hors périmètre glissée au passage

Méthode : lisez d'abord la liste des fichiers modifiés (tout fichier inattendu est suspect), puis les tests, puis le code. Demandez à l'agent : « Qu'est-ce qui pourrait casser avec ce changement ? » Il est souvent lucide sur son propre travail quand on le lui demande.

Sécurité

  • Permissions minimales. N'autorisez pas toutes les commandes shell. Une liste blanche (npm test, npm run lint, git status) couvre l'essentiel.
  • Pas de secrets dans le contexte. Ne laissez pas l'agent lire .env ; interdisez-le dans les réglages de permissions.
  • Méfiance envers le contenu externe. Une issue, une page web ou un README tiers peut contenir des instructions cachées. Un agent qui lit du contenu non fiable ne doit pas pouvoir pousser du code ou envoyer des données sans vous.
  • Mode autonome seulement en bac à sable. Les options qui suppriment toutes les confirmations se réservent à un conteneur jetable, jamais à votre machine principale.

Quand ne pas déléguer

Situation Pourquoi À la place
Vous ne sauriez pas relire le résultat Vous ne verrez pas les erreurs Demandez une explication d'abord, codez ensuite
Aucun moyen de vérifier (pas de tests, UI complexe) L'agent ne peut pas se corriger Écrivez d'abord les tests, ou déléguez par petits morceaux
Décision d'architecture structurante L'agent optimise localement Discutez les options avec lui, décidez vous-même
Code sensible : auth, paiement, crypto Le coût d'une erreur est trop élevé L'agent propose, vous écrivez et relisez à deux
Vous voulez apprendre la techno Déléguer, c'est ne pas apprendre Codez, et utilisez l'agent comme relecteur

Le dernier point compte pour vous en ce moment : pendant cette formation, déléguez l'outillage, mais écrivez vous-même le cœur de chaque projet. C'est là que se fait l'apprentissage.

À retenir

L'agent écrit vite ; c'est à vous de relire bien.

Démo, 45 min

Une commande stats de bout en bout

En 45 minutes, vous faites construire une petite CLI par l'agent en appliquant chaque leçon. Suivez les étapes dans l'ordre et gardez les prompts tels quels la première fois.

  1. 1

    Faire générer le squelette

    10 min
    mkdir demo-stats && cd demo-stats && git init
claude

    Prompt :

    Crée un projet CLI TypeScript minimal :
- Node 20, ESM, TypeScript strict
- commander pour les arguments, tsx pour le dev
- Vitest pour les tests, ESLint pour le lint
- scripts npm : dev, test, lint, build
- une commande `hello` avec son test
Vérifie à la fin que npm test et npm run lint passent.

    Observez la boucle : l'agent crée les fichiers, installe, lance les tests, corrige s'il le faut. Committez : git add -A && git commit -m "squelette".

  2. 2

    Le fichier de contexte

    5 min

    Lancez /init : l'agent analyse le projet et propose un CLAUDE.md. Relisez-le, retirez le superflu, ajoutez une section « À ne jamais faire » en vous inspirant de la Leçon 2. Committez.

  3. 3

    Demander un plan

    10 min

    Passez en mode plan (Maj+Tab), puis :

    Ajoute une commande `stats <dossier>` qui affiche, par extension de
fichier, le nombre de fichiers et le nombre total de lignes, triés
par lignes décroissantes. Ignore node_modules, .git et dist.
Option --json pour une sortie JSON.
La logique de comptage doit être dans src/core/, testée sans
toucher au disque réel (utilise un dossier temporaire dans les tests).

    Lisez le plan. Posez-vous trois questions : les fichiers touchés sont-ils les bons ? Les cas limites sont-ils prévus (dossier vide, fichiers binaires, liens symboliques) ? Les tests vérifient-ils vraiment le comportement ? Corrigez le plan en une phrase si besoin, par exemple : « Ignore aussi les fichiers binaires. »

  4. 4

    Exécuter et observer

    10 min

    Validez le plan. Ne faites rien d'autre : regardez chaque appel d'outil et notez à quel moment l'agent lance les tests, ce qu'il fait quand un test échoue, et s'il sort du périmètre.

  5. 5

    Relire

    10 min

    Créez le sub-agent reviewer de la Leçon 4, puis : « Utilise le sub-agent reviewer sur les changements en cours. » Lisez son rapport, puis relisez vous-même le diff avec la méthode de la Leçon 6. Faites corriger ce qui doit l'être. Testez à la main : npm run dev -- stats . puis npm run dev -- stats . --json.

    Committez. Vous venez de faire le cycle complet : contexte, plan, exécution vérifiée, relecture.

Pratique

Exercices et corrigés

Cinq exercices de 30 à 60 minutes, sur un de vos projets réels ou sur demo-stats. Faites-les avant d'ouvrir le corrigé.

  1. 1Écrire un fichier de contexte

    Sur un projet que vous connaissez bien, écrivez le fichier de contexte : stack, commandes, architecture en 5 lignes, conventions non évidentes, 3 choses à ne jamais faire, 1 piège connu.

    Voir le corrigé

    Un bon fichier se vérifie avec une question : un développeur senior qui découvre le projet lancerait-il les tests correctement et éviterait-il le piège principal rien qu'en le lisant ? Erreurs fréquentes : lister les dépendances (l'agent lit package.json), écrire des règles génériques (« code lisible »), dépasser 200 lignes. Le modèle de la Leçon 2 sert de référence.

  2. 2Mesurer l'effet du contexte

    Choisissez une petite tâche réelle (un endpoint, un composant, un bug). Faites-la une fois dans une branche sans fichier de contexte, une fois avec, dans deux sessions neuves. Notez pour chacune : nombre d'allers-retours, conventions respectées ou non, tests lancés ou non.

    Voir le corrigé

    Le résultat attendu : moins de corrections et des conventions respectées avec le fichier. Si vous ne voyez aucune différence, votre fichier ne contient probablement que ce que l'agent devinait déjà. Ajoutez ce qu'il a raté dans la version sans contexte : c'est exactement ce qui manque.

  3. 3Créer une skill

    Transformez une tâche que vous répétez (écrire un test, rédiger un message de commit, préparer une PR) en skill. Testez-la de deux façons : en l'appelant avec /nom, puis en formulant une demande sans la nommer.

    Voir le corrigé

    Si l'agent ne la déclenche pas seul, c'est la description qui pèche : elle doit dire quoi et quand (« À utiliser quand… »). Exemple de skill de commit :

    ---
name: commit
description: Rédige et crée un commit conventionnel à partir des changements en cours. À utiliser quand on demande de committer.
---

1. Lance git diff --staged (ou git diff si rien n'est indexé).
2. Choisis le type : feat, fix, refactor, test, docs, chore.
3. Titre de 72 caractères max, à l'impératif.
4. Corps : le pourquoi, pas le quoi, en 3 lignes max.
5. Montre le message et attends la validation avant git commit.

  4. 4Un sub-agent relecteur

    Créez le sub-agent reviewer de la Leçon 4, puis introduisez volontairement trois défauts dans un fichier : un cas null non géré, un secret en dur, un test supprimé. Demandez une relecture.

    Voir le corrigé

    Les trois défauts doivent sortir. S'il en manque, précisez le prompt du sub-agent (« vérifie explicitement la gestion de null et undefined », « signale toute chaîne ressemblant à une clé »). Vérifiez aussi qu'il n'a modifié aucun fichier : sans Edit ni Write dans ses tools, il ne peut pas.

  5. 5Un hook de lint

    Ajoutez le hook PostToolUse de la Leçon 4. Demandez une modification contenant une erreur de lint évidente (une variable inutilisée) et vérifiez qu'elle est corrigée ou signalée automatiquement.

    Voir le corrigé

    Si rien ne se passe, trois causes fréquentes : jq n'est pas installé, le matcher ne correspond pas au nom des outils, ou le fichier n'est pas couvert par la config ESLint. Testez la commande seule en lui envoyant un JSON d'exemple : echo '{"tool_input":{"file_path":"src/index.ts"}}' | npx eslint --fix "$(jq -r '.tool_input.file_path')". Dès que le hook grossit, sortez-le dans un script scripts/lint-hook.sh versionné : plus lisible et testable à part.

Projet, 2 à 3 h

Initialiser Repo Assistant

Vous créez le dépôt qui servira de fil rouge à toute la formation, en le faisant construire majoritairement par l'agent. Durée : 2 à 3 h.

Ce que vous livrez

Un dépôt GitHub repo-assistant avec une CLI TypeScript fonctionnelle (une seule commande, info), une CI verte, un fichier de contexte, une skill, un sub-agent, un hook, et un journal de délégation.

Code de départ

Créez ces deux fichiers à la main, puis laissez l'agent faire le reste. Ils fixent les choix techniques pour que tout le monde parte de la même base.

{
  "name": "repo-assistant",
  "version": "0.1.0",
  "type": "module",
  "bin": { "repo-assistant": "dist/cli/index.js" },
  "engines": { "node": ">=20" },
  "scripts": {
    "dev": "tsx src/cli/index.ts",
    "build": "tsc -p tsconfig.json",
    "test": "vitest run",
    "lint": "eslint . && tsc --noEmit"
  }
}
{
  "compilerOptions": {

Les étapes

  1. Squelette. Prompt à l'agent : installer commander, zod, tsx, typescript, vitest, eslint et typescript-eslint ; créer l'arborescence src/cli, src/core, src/llm, tests ; une commande info qui affiche le nom du dépôt courant, sa branche et le nombre de fichiers suivis par git ; les tests associés.
  2. CI. Prompt : un workflow GitHub Actions qui lance npm ci, npm run lint, npm test et npm run build sur chaque push et chaque PR, avec Node 20 et 22.
  3. Contexte. /init, puis réécriture à la main en suivant la Leçon 2. Ajoutez la règle « Appeler un LLM uniquement depuis src/llm/ » : elle servira dès le Module 2.
  4. Outillage agent. Versionnez dans le dépôt la skill write-test, le sub-agent reviewer et le hook de lint.
  5. Une vraie tâche. Faites ajouter une option --json à info, en appliquant plan, exécution, relecture par le sub-agent.
  6. Journal. Tenez docs/journal-agent.md pendant tout le projet (modèle ci-dessous).

Critères de réussite

Validation

Quiz

Six questions. Visez 5 bonnes réponses sur 6 avant de passer au module 2.

  1. Dans la boucle d'un agent de code, qui exécute la commande npm test ?

    Le modèle demande un appel d'outil ; c'est l'application qui l'exécute et lui renvoie le résultat.

  2. Laquelle de ces lignes a le moins sa place dans un fichier de contexte ?

    L'agent lit package.json : l'information n'apporte rien et coûte du contexte à chaque session.

  3. Vous voulez que le formatage soit appliqué après chaque modification, sans exception. Vous utilisez :

    Seul un hook s'exécute à coup sûr. Une consigne ou une skill peut être oubliée.

  4. Quel est le principal avantage d'un sub-agent pour explorer un gros dossier ?

    Le coût total est souvent plus élevé, pas plus bas ; le gain est l'isolation du contexte.

  5. L'agent a fait fausse route pendant 20 minutes. Le plus efficace est généralement de :

    Une session encombrée d'une mauvaise piste continue d'être influencée par elle.

  6. Quelle tâche est la moins adaptée à la délégation complète ?

    Code sensible, coût d'erreur élevé : l'agent propose, vous écrivez et relisez.
